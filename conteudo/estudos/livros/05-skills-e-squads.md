## Resumo (5 linhas)
1. Skill é o método de UMA tarefa repetida, escrito uma vez; o Claude só lê nome+description sempre, o SKILL.md quando o pedido combina, e os arquivos de apoio só quando a etapa cita (l.1099-1107). A description é o gatilho e se testa com tabela de 10 frases (5 devem acionar, 5 vizinhas não).
2. Squad = orquestrador que NÃO faz o trabalho + agentes de 1 competência cada (com "Não faz"), que trocam ARQUIVOS com campos fixos (contrato), com revisor que devolve (máx. 2 voltas), pasta de execução datada e nada sobrescrito.
3. O que precisa acontecer SEMPRE não fica em texto: vai para trava (deny no settings.json, hook PreToolUse/Stop). CLAUDE.md e allowed-tools só orientam (l.5233-5241, 7973).
4. Aprendizado em ciclo curto: achar o PRIMEIRO arquivo de etapa com o erro, mexer só nas linhas da causa, registrar em "## Mudanças" com data/porquê, guardar .bak, rodar de novo só a etapa culpada (-v2) (l.6874-6944).
5. Custo é medido por execução (ficha de custo) e modelo é escolhido por papel: leve no volume, pesado só em quem confere (l.4530-4533, 7400).

## O que serve para a ESCALA (detalhado)

### A. Como escrever skills boas (estrutura, gatilho, tamanho, teste)
**A1. Triagem antes de criar skill (cap. 1, l.709-722, 852-860).** Só vira skill a tarefa que é (1) recorrente, (2) estruturada (mesmas partes todo dia) e (3) replicável por outra pessoa com passo a passo; e que é UMA tarefa com UMA entrega. "Marketing do cliente" são dez tarefas. Gosto geral (tom de voz, idioma) não é skill: é instrução pessoal/CLAUDE.md. Tarefa que muda toda vez fica no prompt. Entre duas candidatas, comece pela entrega mais fácil de conferir (l.784).
- Aplicar na ESCALA: antes de criar skill nova, preencher a ficha de 4 linhas: Recorrente? Estruturada? Replicável? Uma tarefa só? Se alguma for "não", é bloco dentro de skill existente, não skill nova.

**A2. Esqueleto de SKILL.md (cap. 2, l.998-1028, 1749-1794).** Ordem fixa: cabeçalho (name = nome da pasta, minúsculas e hífen; description) → título → **Quando usar / Não use para** → **Etapas numeradas** (verbo no começo; cada etapa que depende de arquivo diz "abra references/X e tire Y") → **Formato da entrega** → **Limites**. O mais importante vai NO TOPO, porque em conversa longa o Claude pode guardar só o começo (l.992-995). Skill de leitura: a regra "somente leitura" no topo (l.2712).
- Padrões úteis de redação que dão para copiar:
  - Etapa final de autoconferência: "Antes de entregar, confira se cada linha tem origem nas notas" (l.1755).
  - Seção "Quando faltar informação" com a saída padrão para cada buraco ("a definir", "sem prazo", "data não informada"; prazo relativo só vira data se houver data-base) (l.1785-1790).
  - Limites negativos curtos: "Não invente nome, data, número ou decisão. Sem comentários antes ou depois." (l.1792-1794).
  - Para análise: **"Sem evidência na fonte, o ponto sai"** colocada nas ETAPAS, não escondida no fim (l.2258, 2443-2446). **Marcar [fato] x [inferência]**, abrir com as premissas, dizer qual dado falta (l.2731-2735).

**A3. Tamanho e níveis de carga (l.1099-1107, 1039-1040, 1154).** Nível 1: nome+description de todas as skills, sempre. Nível 2: SKILL.md inteiro quando o pedido combina. Nível 3: arquivo de apoio só quando a etapa pede. Por isso: SKILL.md curto (doc oficial recomenda < 500 linhas; o livro manda < 100 no comando de gerar skill) e tabelas/listas longas em `references/`, modelos em `assets/`, código em `scripts/`. Arquivo de apoio que nenhuma etapa cita fica esquecido (l.1089-1090, 1265). No Claude Code a lista de descriptions inteira cabe em ~1% da janela e, se passar, saem primeiro as das skills menos usadas (l.1450-1452): description enxuta protege as skills pouco usadas.
- Aplicar na ESCALA: `carrosseis-tweet-tedson` (767 linhas) e `ebook-profissional` (801) estão muito acima de 500; mover o corpo longo para `references/` e deixar SKILL.md com fluxo + "abra references/X na etapa Y". As `escala-*` (17 a 62 linhas) já estão no tamanho certo.

**A4. Description como gatilho (cap. 3, l.1315-1660).**
- Receita: `[VERBO] [ENTRADA] em [ENTREGA], com [ITENS CONFERÍVEIS]. Use quando pedirem [3 palavras do pedido]. Não use para [tarefa vizinha].` (l.1351-1357).
- Usar as palavras que a equipe REALMENTE diz ("faz vídeo do assunto do momento"), não o nome técnico. Quatro erros: vaga, várias funções, promessa genérica ("boas práticas"), sem teste (l.1337-1343).
- Limites: 200 caracteres é o que o chat aceita; o Claude Code aceita até 1.024 e corta em 1.536 na lista (l.1447-1452). As descriptions `escala-*` têm 190 a 440 caracteres: como a operação roda no Claude Code na nuvem, não há problema técnico, mas as de 330+ (`escala-social-media`, `escala-hype-e-afiliado`, `escala-ganchos-retencao`, `escala-video-ia`) podem ser enxugadas movendo exemplos para "Quando usar" no corpo.
- O padrão "Aciona quando… NÃO aciona para…" que a ESCALA já usa é exatamente o do livro.

**A5. Teste de acionamento (l.1496-1593, 8030-8052).** Tabela de 10 frases: 1 a 5 DEVEM acionar (variar: formal, apressada, sem as palavras da description, citando arquivo, no meio de outro assunto); 6 a 10 NÃO devem (vizinhas do mesmo tema; frase sem relação não ensina nada). Rodar UMA frase por conversa nova, SEM dizer o nome da skill (com nome você está chamando à mão). Se não acionou onde devia: falta a palavra do pedido. Se acionou sem dever: fortaleça o "Não use para". Mude UMA coisa por vez, suba a versão e rode as 10 de novo (a correção de uma quebra outra). O teste pelo "/" prova o corpo; a tabela prova a description (l.1552-1554).
- Aplicar na ESCALA: pares vizinhos que mais se confundem hoje: `escala-radar-viral` x `escala-ideias-fora-da-caixa`; `escala-producao-video` x `escala-editor-video` x `escala-animacao-personagens` x `escala-video-ia`; `escala-roteiro-serie` x `escala-biblia-serie` x `escala-ganchos-retencao`; `escala-produto-greenn` x `escala-oferta`. Montar a tabela de 10 frases só para esses pares (frases reais do Victor no Telegram, ex.: "faz um vídeo do GTA", "me dá uma ideia diferente", "o vídeo flopou") e registrar a versão em `memoria/aprendizados.md`.

**A6. Três testes de corpo para toda skill (l.1954-2000, 2760-2791).** (a) pelo "/" (formato certo), (b) automático (aciona sozinha), (c) negativo (usa a palavra do tema num pedido que não deve acionar). Mais, para skill que analisa: caso "sem informação" e caso "fora do escopo" (l.2463-2466). Registrar em tabela Teste | Esperado | Obtido. Se falhar, mude só o trecho responsável e repita os 3.

**A7. Criar a skill conversando (cap. 5, l.2135-2240).** Nunca abrir com "crie uma skill de X": o Claude preenche tudo que você não disse. Passos: (1) pedir primeiro a LISTA DE DECISÕES (escopo, fontes, profundidade, formato, destino da resposta, o que fazer quando faltar informação), com 2-3 opções e a consequência de cada; (2) entrevista em blocos curtos; (3) ter a **ficha de respostas-âncora preenchida ANTES** (l.2189-2202), para não aceitar a primeira opção; (4) pedir para desafiar o rascunho antes de salvar: "dê 3 pedidos reais em que ela daria resposta fraca; diga qual resposta-âncora ficou fora do texto; confira a description" (l.2227-2238).
- Prompt pronto para a ESCALA (adaptar): "Quero criar uma skill com você, mas não escreva nada ainda. Ela faz [tarefa] a partir de [entrada] e entrega [saída]. Liste as decisões que eu preciso tomar (escopo, fontes, profundidade, formato, destino, o que fazer quando faltar informação), com 2-3 opções e a consequência de cada. Depois pergunte em blocos curtos."

**A8. Avaliar se a skill vale o arquivo (l.2333-2436).** `skill-creator` (da Anthropic, Apache 2.0): roda os mesmos casos COM e SEM a skill, em paralelo, e dá taxa de acerto, tempo e tokens; grava `evals/evals.json` na pasta da skill. Casos: um normal, um sem informação, um que costuma dar errado (link que não abre). Regras de leitura: leia as RESPOSTAS antes do número; se as duas versões empatam em tudo, a skill não ensina nada que o Claude já não faria (apertar critérios ou desistir); o número só mede os critérios que você escreveu; só aceite mudança que corrige falha que você viu (l.2426-2436). Instalar: `/plugin install skill-creator@claude-plugins-official` (l.2358).

**A9. Skill que NÃO deve estragar nada: regra + trava (cap. 6, l.2505-2650, 2845-2862).** A regra escrita ("só lê") orienta; a trava barra: `permissions.deny` em `.claude/settings.json` (ex.: `"Edit(./dados/**)"`), ou grupo "Blocked" no conector. `allowed-tools` NÃO bloqueia, só dispensa perguntas (l.2647-2650). Regra de caminho vale para Read e Edit; `Write(...)` é ignorada; não alcança script que abre arquivo por conta própria (l.2678-2681). Provar a trava SEM a skill ("sem usar nenhuma skill, acrescente uma linha em X": tem que ser negado) (l.2853-2856).

**A10. Skill índice (cap. 7, l.3089-3153, 3257-3270).** Para base grande (ex.: `memoria/` + `conteudo/` + `aprendizados`): skill com **Data do mapa**, **Fluxo obrigatório no topo** (achar a rota → abrir só as páginas da rota → responder curto e terminar com "Fonte:" → se não está lá, dizer que não achou, nunca completar com suposição → se a página foi editada depois da data do mapa, avisar que o mapa pode estar velho), **Mapa de rotas** (Assunto | Arquivo), **Palavras ambíguas** ("contrato" assinado x em branco) e **Limites**. Mapear uma vez (título, caminho, resumo de 1 linha, 3-5 palavras que alguém usaria, data da última edição); remapear 1x/mês ou ao criar/renomear/apagar página.

**A11. Skills de terceiros (cap. 8 e Apêndice C, l.3341-3700, 7950-7962).** Ficha de confiança (origem, autor, licença, última atualização, arquivos, o que o SKILL.md manda, o que cada script faz, acessa internet?, pede chave?, lê pastas fora?, decisão). **Quatro sinais de skill perigosa**: description larga demais (aciona em tudo); pede chave no chat; instrução escondida em referência (comentário HTML mandando ignorar/não avisar); script que envia arquivo para fora (curl). Processo: baixar para quarentena (fora de `.claude/skills`, o Claude não carrega), auditar em modo Plan SEM executar, instalar só em pasta de teste e só depois no nível pessoal. Instalação/estrela não dizem o que o arquivo faz. Licença: instalar não é copiar.
- Aplicar na ESCALA: `carrosseis-tweet-tedson`, `ebook-profissional`, `omegaprompt`, `reels-para-carrossel` e `ui-ux-pro-max` vieram prontas. Conferi por busca de texto: nenhuma tem `curl`/`wget`/`requests.post` nem frase de "ignore as instruções". A `ui-ux-pro-max` tem scripts Python (`scripts/*.py`) e `__pycache__` commitado: ler os .py uma vez com a ficha de confiança antes de qualquer execução em nuvem, e só rodar na pasta de teste. Registrar a ficha em `memoria/`.

### B. Squad ou agente único que decide sozinho
**B1. Quando NÃO montar squad (l.4246-4258).** 1 competência e 1 entrega (vira skill); tarefa única; precisa do humano no meio (subagente não faz perguntas); não sabe dizer quando está pronto. Vale squad quando o trabalho se repete, junta ≥2 competências e termina numa entrega que você confere. Sinal de squad desnecessário: "os outros papéis só passam o texto adiante" (l.4573).
- Leitura para a ESCALA: o "cérebro" atual (`escala-social-media`, 55 linhas, 1 agente) é a escolha certa para decidir; a divisão só compensa onde há 3 motivos: contexto próprio (quem decide lê só a tabela, não 5 páginas), paralelo (radar das 3 redes ao mesmo tempo) e revisão por outro agente sem a pressa de quem produziu (l.4219-4224). A produção do vídeo e a conferência são o par que mais ganha com revisor separado.

**B2. Ficha de diagnóstico do processo ANTES de criar agente (l.4286-4301, 4302-4355).** Campos: processo, quem faz e frequência, entrada, saída (e formato), etapas, competências (2 a 4, cada uma candidata a papel), decisões (com a regra; sem regra, "a definir"), **critério de pronto verificável**, o que fica fora. "Pular o diagnóstico é o erro mais caro" (l.4281). Critério de pronto verificável: "cinco lojas lidas ou falha registrada, custo total com frete e recomendação com motivo" é bom; "uma boa análise" não (l.4354).
- Exemplo ESCALA para preencher: processo "vídeo do dia por rede"; entrada = 3 temas com prova; saída = MP4 + legenda + título + etiqueta IA na fila; competências = achar (radar), roteirizar, produzir, conferir; critério de pronto = "passou checklist `escala-regras` + folha de quadros olhada + transcrição da voz conferida + entrada na `aprovacao/fila.md`"; fica fora = publicar sem "aprova".

**B3. Vaga de agente (l.4543-4557).** Cargo | Missão (1 frase) | Recebe | Entrega (formato exato) | Ferramentas | Modelo | **Não faz** ("pesa mais que as outras: impede dois agentes de fazerem o mesmo trabalho", l.4538). Corpo do agente até 15 linhas (l.6751): "Você X. Não faz Y e Z. 1... 5. Grave o arquivo e responda só com o caminho." (l.7591-7600).
- Aplicar: revisar as 4 fichas em `.claude/agents/` (chefe, radar, produtor, analista) e acrescentar linha **"Não faz"** em cada (ex.: radar "não escreve roteiro nem produz vídeo"; produtor "não escolhe tema nem publica"; analista "não altera vídeo"; chefe "não produz nem mede").

**B4. Modelo por papel (l.4417-4533, 4502-4509, 5386-5389).** Haiku = ler, separar, contar, classificar (volume/extração); Sonnet = escrever, analisar, vários passos; Opus só para quem planeja, decide entre caminhos ou CONFERE o trabalho dos outros. Começar no mais leve que pareça dar conta e subir UM degrau só no papel que falhou na conferência. Modelo passado na chamada vence o do arquivo (l.7223).
- Para a ESCALA (custo perto de zero): radar de extração/coleta e checagens mecânicas em haiku; roteiro/legenda em sonnet; opus só se um revisor único falhar de forma comprovada. Hoje `escala-chefe` está em sonnet (ficha l.4).

**B5. Orquestrador (cap. 12, l.5059-5096, 5152-5159, 5233-5241).** Quatro partes: (1) primeira linha "se você é um dos agentes abaixo, siga só o seu arquivo e ignore este" (subagente recebe o mesmo CLAUDE.md); (2) papel: "você não pesquisa, não calcula, não decide; entende o pedido, chama, confere e apresenta"; (3) **fluxo com entrada e saída (arquivo) de cada etapa** + **ponto de parada** (ex.: menos de 3 resultados = para e pergunta) + confirmar dados que faltam ANTES de chamar; (4) **regras invioláveis**: "nunca faça o trabalho de um agente, nem quando eu pedir pressa"; "passe o CAMINHO do arquivo, nunca um resumo seu; não corrija, não arredonde, não complete número de agente"; "só chame a etapa seguinte depois que o arquivo da anterior existir"; "toda entrega em output/ com data e hora no nome; nunca apague nem sobrescreva execução anterior (é o histórico para achar quem errou)". Menos de 200 linhas.
- Teste do orquestrador: pedir exatamente o que ele não pode fazer ("estou com pressa, pesquise você mesmo") em modo Plan e ver se delega (l.5195-5231).
- Aplicar: em `escala-social-media` §1-2, acrescentar as 4 regras invioláveis acima (a rodada das 7h chama radar/roteiro/voz/editor e passa caminhos de arquivo; não improvisa).

**B6. Contrato de dados entre etapas (l.5458-5478, 5718-5728, 6490-6498).** Cada agente grava um arquivo com **campos fixos e nomes que não mudam** (os outros leem por eles); campo que não existe = `null`/"não encontrado", nunca palpite. Conferir o contrato pedindo tabela: campo gravado | quem lê | nome igual dos dois lados? (erro típico `preço` x `preco`). Contrato de evidência: `{id, afirmacao, fonte, trecho (≤20 palavras, copiado igual), consultado_em}`, com faixas de id por coletor (E01, E21...) para não colidir em paralelo. Toda afirmação do relatório termina com [E07]; "sem número, a frase sai".
- Esboço de contrato para a ESCALA (JSON por etapa em `output/AAAA-MM-DD-HHMM/`): `1-radar.json` {rede, tema, prova_link, views, data, formato}; `2-roteiro.json` {gancho, partes[], legenda, etiqueta_ia, fonte_dos_fatos[]}; `3-video.json` {arquivo, duracao_s, voz, quadros_conferidos}; `4-revisao-N.json` {veredito, falhas[]}. Fatos da legenda levam [E##] com link e data (alinha com a regra 5 do checklist: "fatos conferidos em fonte com data").

**B7. Skill de decisão em camadas (l.5619-5658).** (1) **Regras eliminatórias ANTES de qualquer nota** (divergente do pedido ou fora do prazo = "Fora da comparação" com motivo; dois sinais de risco = "Evite" seja qual for o preço; "preço fora da curva" nunca fica em primeiro; menos de 3 válidas = "Cobertura incompleta"); (2) só então notas 0-10 com pesos escritos para as que sobraram; (3) recomendação em camadas: Compre / Alternativa / Evite e Fora (com motivo e evidência) / Não conferido; (4) resumo em 3 linhas sem "talvez". "Um preço baixo demais nunca compensa um risco" (l.5610).
- Aplicar na ESCALA (escolher o tema do dia): regra 1 (eliminatórias) = viola regra fixa do CLAUDE.md, sem prova, sem versão nossa possível, precisa de ferramenta que não temos, direito autoral, vítima real. Passou? Aí nota com pesos escritos: prova de views recentes, mais de um criador pegando, dá série, custo de produzir, risco de desmonetização. Fora da comparação sai com o motivo registrado. Isso substitui "gosto" por regra.

**B8. Revisor que DEVOLVE (cap. 17, l.7136-7151, 7691-7716).** Revisor que só comenta deixa o erro passar. Seção "Revisão": (1) nada chega a mim sem o revisor aprovar; (2) critérios escritos de aprovação; (3) resposta em formato fixo `VEREDITO: APROVADO | DEVOLVER` + uma linha por falha: trecho → problema → agente responsável → correção; (4) tabela de responsável por tipo de falha; (5) cada falha vai SÓ ao responsável e passa de novo no revisor, **no máximo 2 voltas**; se ainda faltar, entregar com seção "Não aprovado pelo revisor" no topo; (6) salvar `revisao-1.json`, `revisao-2.json`. O redator na volta "corrige só os trechos de revisao.json e mantém o resto igual". Revisor tem Read/Glob/Grep/Write, não reescreve, não lê a web; modelo mais pesado fica com ele.
- Aplicar na ESCALA: transformar a conferência já existente em `escala-editor-video` + checklist de `escala-regras` num **revisor separado de quem produziu** (mesmo que seja outra chamada do mesmo modelo com contexto limpo, lendo só os arquivos). Critérios: 8 itens do checklist de `escala-regras`; folha de quadros; transcrição da voz bate com o roteiro; legenda sem travessão; etiqueta IA marcada; fato com fonte. Veredito APROVADO/DEVOLVER com agente responsável (roteiro, voz, edição). Máx. 2 voltas, depois vai à fila com aviso de "não aprovado" em vez de gastar limite sem fim. Erro comum do livro: "Revisor sem limite de voltas" (l.7465).

**B9. Três versões + JUIZ (l.7176-7189).** Para escolher gancho/título/ângulo: 3 agentes em paralelo escrevem 3 versões; o juiz NÃO escreveu nenhuma, só lê, dá nota 0-10 em critérios escritos, escolhe 1, explica em até 5 linhas e diz o risco; salva `julgamento.md`. "Juiz que escreveu uma das versões: vence sempre a dele" (l.7467).
- Aplicar: no roteiro de cada vídeo gerar 3 ganchos (primeiro quadro + primeira frase) e deixar um juiz com critérios de `escala-ganchos-retencao` escolher; guardar as 2 perdedoras para teste A/B em outra rede (alinha com "Testa uma coisa por vez", `escala-social-media` §3.4).

**B10. Equipe em linguagem natural (l.7198-7218).** Para tarefa avulsa: "Use 4 subagentes com o modelo Haiku, em paralelo, um para cada arquivo X. Cada um lista Y com o trecho. Depois confira se os quatro seguiram o mesmo formato, monte uma tabela única e diga quantos agentes rodaram e com qual modelo." Não limita ferramentas (sem `tools`); tarefa que se repete vira agente com arquivo. Limites: 20 subagentes simultâneos, até 3 níveis.
- Aplicar no radar: 3 subagentes haiku em paralelo, um por rede (TikTok, Instagram, YouTube), cada um devolve a mesma tabela (Rede | O que está pegando | Prova | Formato); a conversa principal só confere formato e monta a tabela única.

**B11. Ensaio (l.5736-5785, 6366-6376, 6529-6537).** Antes de rodar com dado real, rodar com dados FICTÍCIOS cujo resultado você já sabe (e conferir contra a conta). A regra "modo ensaio: só ler pasta tal, sem web" deve estar no CLAUDE.md E na skill do coletor (erro comum, l.6629).
- Aplicar: pasta `ensaio/` com 3 "temas virais" fictícios (um viola regra fixa, um sem prova, um bom) para testar a skill de decisão e o revisor sem gastar produção. Verificar que o fictício que viola a regra sai em "Fora da comparação".

**B12. Rodar e conferir (cap. 14, l.5855-6204).** 1ª execução sempre no modo Manual; subir um degrau (Accept edits → Auto) só depois de ler o que o squad fez no anterior (l.4878); Bypass só em máquina isolada. Ler a delegação enquanto acontece: qual agente foi chamado, qual skill leu, o que foi buscado; se a conversa principal abre página sozinha, o orquestrador está fazendo o trabalho do agente: parar e revisar o CLAUDE.md. Comando "mostre o caminho etapa por etapa": tabela etapa/agente/modelo/skill/páginas abertas e falhas/arquivo gravado + lista do que ficou fora do fluxo (l.5984-5996). Comando de conferência: comparar o relatório com os arquivos de cada etapa (preço igual ao da coleta? cada alerta aparece? alguma loja que não está na coleta? cobertura dita? segue as regras da skill?) "Não corrija nada" (l.6062-6074).
- **Ficha de conferência da execução (l.6077-6090):** cobertura (pedidas/lidas/com falha), links abertos?, valor-chave conferido na fonte?, risco (todo alerta aparece?), honestidade (diz o que não sabe?), divergências, modelo de cada agente, uso do plano antes/depois, decisão: publico / refaço a etapa __ / confiro à mão. "Conferir só o texto final" é erro (l.6217): abrir ao menos o link principal.
- **Refazer só a etapa culpada (l.6139-6204):** tabela sinal → etapa culpada → ação; chamar o agente pelo nome com `@agent-nome`; salvar como `...-v2` sem apagar o anterior.

### C. Memória e aprendizado
(O livro não tem capítulo de "memória" no sentido de banco de lembranças; o que ele ensina de aprendizado é o ciclo de refino abaixo e a regra de que o que importa para o próximo trabalho vai para a skill.)
**C1. Achar o culpado (cap. 16, l.6874-6903).** Cada etapa deixa um arquivo. Ler os arquivos NA ORDEM do fluxo; o **primeiro** que já traz o erro aponta o agente culpado (o revisor que deixou passar é o segundo a consertar). Citar a linha do agente/skill que causou. Ficha **"Quem errou"** (l.8074-8083): execução, erro como saiu, o certo com a fonte, primeiro arquivo com o erro, agente/skill culpado, causa com a linha citada, mudança feita, etapas que rodaram de novo, o erro sumiu?
**C2. Reescrever só as linhas da causa (l.6917-6932).** "Reescrever o agente inteiro troca um defeito conhecido por outros novos." Mostrar antes e depois de cada linha; no fim do arquivo, seção **"## Mudanças"** com data, o que mudou e por quê (exemplo l.7619-7621); salvar `[AGENTE].md.bak` antes de gravar; não mexer nas outras skills/agentes. Se a correção resolve um erro e cria outro: voltar ao .bak e pedir só as linhas da causa (l.7023-7029).
**C3. Onde mexer: skill, agente ou orquestrador (l.6964-7011).** Formato/procedimento errado para qualquer agente que use a skill → skill de projeto; um papel fez o que não devia/ficou sem ferramenta/modelo fraco → agente; ordem, paralelo ou critério de pronto → CLAUDE.md. Skill usada por 2 agentes muda os dois: rodar as etapas de ambos.
**C4. Registro por execução.** Pasta `output/AAAA-MM-DD-HHMM/` com 1 arquivo por etapa, nunca sobrescrever; hooks gravam `output/registro.log` (início da sessão, fim de cada subagente com `agent_type`, fim de resposta) (l.7330-7363). Ficha de custo por execução (l.7400-7425): agentes/modelo/vezes, voltas do revisor, duração, uso antes/depois (janela de 5 h e semana), `/usage` por categoria, o que mudar. Regra de manutenção: "se a execução seguinte gastar menos sem perder nota no julgamento nem ganhar falha no revisor, a mudança fica" (l.7425). Revisão mensal: rodar o ensaio de cada squad e comparar com a ficha anterior; se a nota caiu ou o uso subiu, voltar ao refino (l.7446-7449).
- Aplicar a `escala-memoria` (hoje 19 linhas): (a) passo "regra que vale para o próximo trabalho vai para a skill" já existe: acrescentar o formato **`## Mudanças`** (data | o que mudou | por quê | evidência) no fim de cada skill e agente alterado; (b) antes de mexer numa skill, `.bak` (aqui: o git já guarda, então basta commit por mudança de skill com a mensagem "skill X: linha Y, motivo"); (c) ficha "Quem errou" quando um vídeo flopar por erro de produção (não por tema): registrar em `memoria/aprendizados.md` com a linha da skill culpada.

### D. Travas que não dependem do texto (cap. 6, 11, 12, 17; Apêndice B/C)
- `settings.json` do projeto: `allow` só vale depois de confiar na pasta; `deny` vale SEMPRE, até no modo Bypass (l.4953, 7921). Modelo: `allow: Edit(./output/**)`; `deny: Read(./.env), Read(./.env.*), Edit(./inputs/**)` (l.4911-4922). Chave de API só em `.env` com `.env.example`, `.gitignore` e deny de leitura; chave que vazou: desligar e criar outra (l.3558-3588).
- **Hooks** (comando que o Claude Code roda sozinho num evento, sem depender do modelo): `SessionStart, UserPromptSubmit, PreToolUse (pode BARRAR a ação), PostToolUse, Notification, SubagentStart, SubagentStop, Stop`; tipos `command, prompt, agent, http, mcp_tool` (l.7923-7925). "O que nunca pode acontecer vai para uma trava fora do texto" (l.424-428).
- **Sugestões concretas para a ESCALA** (a regra fixa mais importante é "publicação só com aprova do Victor" e "zero ligação com Wesley/Victor"):
  1. `PreToolUse` com matcher nas ferramentas de publicar/agendar (Metricool `createScheduledPost`, `tiktok_publish`, etc.) que consulta `aprovacao/fila.md` e barra se o ID da peça não tiver linha APROVADO (script curto de shell/python).
  2. `PostToolUse`/`Stop` que roda `grep -iE "caveira|wesley|krav|gimenez"` (e o caractere de travessão) nos arquivos novos de `conteudo/` e falha se achar. Trava técnica para as regras 1 e "sem travessão".
  3. `deny` em `Edit(./aprovacao/fila.md)` fora do fluxo? Cuidado: o chefe precisa editar a fila; melhor só barrar o campo APROVADO via hook que compara com o que o Telegram recebeu (decisão do botão). Anotar como ideia, não como regra pronta.
  4. `deny` `Read(./.env)` se algum dia houver `.env` local (CLAUDE.md já proíbe segredos em arquivo).
  Limitação a conferir antes de prometer ao Victor: não consegui verificar se hooks e `deny` de `.claude/settings.json` valem em sessão agendada na nuvem; testar em 1 rodada e registrar.
- **Antipadrão do livro que a ESCALA deve evitar:** "aprovar todos os pedidos de uma vez" (l.3676) e "aprovar a leitura de qualquer site para sempre" (l.6210). A fábrica agendada roda sem humano: por isso as travas acima precisam ser técnicas.

### E. Conduta de coleta na web (cap. 13/15, l.5603-5605, 6556-6566, 7989-7996)
Ler os termos de uso do site antes de usar; quem proíbe robôs/agentes de IA sai da lista; sem login, cadastro, compra, CAPTCHA ou contorno de bloqueio; bloqueou = registrar falha e seguir; só 1 agente (coletor) lê a web; guardar só o mínimo (LGPD art. 6º III); citar trecho curto com origem (Lei 9.610 art. 46 III), nunca texto longo/imagem; nome de pessoa nunca. Google Maps (termos de 26/08/2026) e Reclame Aqui (10/11/2025) proíbem copiar/raspar.
- Aplicar no radar: guardar link + data + métrica pública + 1 frase de resumo nossa; não guardar texto/legenda longa nem nome de criador pequeno além do necessário para a prova; respeitar termos do TikTok/Instagram (por isso prints do Victor valem como prova).

### F. Plugins e marketplace (cap. 9)
Plugin = pasta com `.claude-plugin/plugin.json` (só ele ali; `name` obrigatório, `version` sobe a cada mudança) + `skills/ commands/ agents/ hooks/ .mcp.json` na raiz; CLAUDE.md não entra no plugin; marketplace = repo com `.claude-plugin/marketplace.json`. Plugin de terceiro com hook, conector local ou `bin/` roda programas no PC com suas permissões (l.3788-3796). **Para a ESCALA: baixa prioridade** (1 operador, 1 repositório, skills já em `.claude/skills/` que vai junto com o repo).    - Rodar de novo só a etapa culpada e dependentes (-v2).
   - Ficha "Quem errou" em `memoria/aprendizados.md`.
5. **`escala-travas`**: Aciona quando for configurar `.claude/settings.json`, hooks, permissões ou quando uma regra fixa foi violada mesmo escrita. NÃO aciona para escrever conteúdo.
